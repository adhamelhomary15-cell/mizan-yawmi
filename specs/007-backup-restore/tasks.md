# Tasks: Backup and Restore

**Input**: Design documents from `specs/007-backup-restore/`

**Prerequisites**: [plan.md](plan.md), [spec.md](spec.md), [research.md](research.md), [data-model.md](data-model.md),
[contracts/ui-contract.md](contracts/ui-contract.md), [quickstart.md](quickstart.md)

**Tests**: Requested by the plan (R10): a dev-only `tools/check-backup.js` with a mutation self-test, run in CI.
Browser checks follow [quickstart.md](quickstart.md) at 375 px.

**Organization**: Grouped by user story. The plan's phases map as follows: plan 1 = Phase 2 here, plan 2 = Phase 3,
plan 3 = Phases 4 and 5, plan 4 = Phase 6, plan 5 = Phase 7.

**Cut points** (one branch and PR each):
- **A**, after Phase 3: saving works on its own and is safe to ship.
- **B**, after Phase 5: restore ships only together with every rejection, because a restore without its
  guards could damage the data it is meant to protect.
- **C**, after Phase 7: persistent storage and polish.

## Format: `[ID] [P?] [Story] Description`

- **[P]**: Can run in parallel (different files, no dependencies)
- **[Story]**: US1 (save), US2 (restore with preview), US3 (bad files change nothing), US4 (keep the browser
  from clearing data)
- Every behaviour change is in `src/planner.html` (single-file app). `index.html`, `sw.js` and the manifest are
  generated by `tools/build.py` and are never edited by hand.

## Binding rules for every task

- Constitution v2.0.0 Principle II: the only path that writes done marks is a restore the owner confirmed after
  a preview, and it writes the file's marks exactly. Nothing adds, removes or changes a mark.
- Principle III: no network call anywhere in this feature. Use no `fetch`, `XMLHttp`, `sendBeacon` or WebSocket.
  The share sheet runs only on the owner's tap.
- Principle VI: no real backup or personal data in any tracked file. Tests generate generic data. Run
  `node tools/check-private.js` with the files staged before every commit.
- Copy is Egyptian Arabic, right to left, taken word for word from
  [contracts/ui-contract.md](contracts/ui-contract.md). Dates and counts use Latin digits inside `<bdi>`. Every
  control is at least 44 px.

## Phase 2: Foundational: the backup rules and their check (plan phase 1)

**Purpose**: Pure, tested rules every story uses. **The app's behaviour does not change in this phase**: the
new code is not called yet.

**⚠️ CRITICAL**: No story work starts until T003-T007 pass.

- [x] T003 Add a marked block `// start of backup rules` … `// end of backup rules` in `src/planner.html`
  after `// end of workout rules`. It uses no storage, no DOM and no `navigator`. It holds:
  - `const BACKUP_FORMAT = 'mizan-backup'`, `const BACKUP_VERSION = 1`, and
    `const BACKUP_MAX_BYTES = 5 * 1024 * 1024`.
  - `fnv1a(text)`: FNV-1a 32-bit hash of the UTF-16 code units, returned as "8 lower-case hex digits".
  - `makeBackup({progress, workouts, settings}, now, dateIso)`:
    - It returns `{text, name}`.
    - `text` is `JSON.stringify({format, version, createdAt: new Date(now).toISOString(), checksum, data})`,
      where `data = {progress, workouts, settings: settings || null}` and `checksum = fnv1a(JSON.stringify(data))`.
    - `name` is `'mizan-backup-' + dateIso + '.json'`, with the date in the app's time zone, passed in by the
      caller.
- [x] T004 In the same block, add `readBackup(text, {normalize, normalizeRoot, validateSettings})`. It returns
  `{ok: false, code}` or `{ok: true, parts, preview}`, checking in this order:
  - Blank or whitespace text gives `empty`. Text that does not parse as JSON gives `not-json`.
  - An object with `format === 'mizan-settings'` gives `settings-file`. Any other object without
    `format === 'mizan-backup'` gives `not-backup`.
  - A `version` that is not a whole number ≥ 1 gives `damaged`. A version above 1 gives `too-new`.
  - It gives `damaged` when any of these hold: `createdAt` does not parse as a date; `data` is not an object;
    `data.progress` or `data.workouts` is not an object; `data.settings` is neither `null` nor an object; or the
    checksum is missing or does not equal `fnv1a(JSON.stringify(data))`.
  - `normalizeRoot(data.workouts).tooNew` gives `too-new`.
  - Otherwise `parts = {progress: normalize(data.progress), workouts: normalizeRoot(data.workouts).root,
    settings, settingsValid}`:
    - `settingsValid` is `'none'` when `data.settings` is `null`.
    - It is `'valid'` when `validateSettings(data.settings).ok`; `settings` is then the validated object.
    - Otherwise it is `'invalid'`, and `settings` is `null`.
  - `preview = {createdAt, tasks, appts, courses, tickDays, workouts, openWorkout, settings: settingsValid}`.
    The counts are the lengths of the progress lists. `tickDays` is the number of keys in `checks`. `workouts`
    is the number of finished workouts. `openWorkout` is whether `workouts.current` is set.
  - It never throws. The progress part is used as normalised and never edited (R5).
- [x] T005 [P] Create `tools/check-backup.js`, a dev-only Node script in the style of `tools/check-workout.js`:
  - It loads the backup rules block from `src/planner.html`, plus the real `normalizeRoot` from the workout
    rules block.
  - It loads `validateSettings` the way `tools/check-settings.js` does (`grabFunction`).
  - For `normalize` it uses a small stand-in that copies the progress shape, because the real one depends on
    settings-derived constants.
  - All data is generated and generic. Exit codes are 0 (pass), 1 (fail) and 2 (usage).
- [x] T006 In `tools/check-backup.js`, write these checks:
  - **Round trip:** `makeBackup` then `readBackup` gives the same parts, and the preview counts match.
  - **Marks:** the restored `checks` and `modules` deep-equal the file's, with nothing added or dropped.
  - **Settings:** `null` gives `none`; a valid settings object gives `valid`; a broken one gives `invalid` with
    `settings: null`.
  - **Rejections:** one check per code: `empty`, `not-json`, `settings-file`, `not-backup`, `too-new` (version 2,
    and a workouts part with `v: 2`), and `damaged`. For `damaged`, test a missing part, a wrong type, a bad
    `createdAt`, a missing checksum, and a one-character edit inside `data` with the checksum left as it was.
  - **Checksum:** it is stable for the same input and differs after the edit.
  - **File name:** `mizan-backup-YYYY-MM-DD.json` holds nothing else.
  - **Never throws:** `readBackup` on 200 random strings and objects.
  - **Timing:** 700 workouts of 10 exercises × 4 sets plus 730 days of ticks: make and read together take under
    500 ms in Node.
  - **Isolation:** the block contains no `localStorage`, `navigator.`, `fetch(`, `XMLHttp`, `sendBeacon` or
    `WebSocket`, ignoring comments.
- [x] T007 Add `--self-test` to `tools/check-backup.js` with one mutation per rule, which the checks MUST notice:
  - the checksum is skipped;
  - a version of 2 is accepted;
  - a settings file is accepted as a backup;
  - invalid settings are kept;
  - `tickDays` counts the wrong thing;
  - a mark is dropped on read;
  - the size constant is raised;
  - a damaged part is accepted.

  Then add a «Backup rules» step to `.github/workflows/checks.yml` that runs `node tools/check-backup.js` and
  `--self-test`, beside «Workout rules».

**Checkpoint**: The new checks and their self-test pass, and so do all the existing checks. A rebuild produces the
same app behaviour. Commit as `feat(backup): backup rules and their check (007)`.

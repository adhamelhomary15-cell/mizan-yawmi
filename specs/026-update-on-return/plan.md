# Implementation Plan: New Versions on Return, and the Version in Settings

**Branch**: `026-update-on-return` | **Date**: 2026-10-24 | **Spec**: [spec.md](spec.md)

## Summary

Two small changes, with no new library:
- **On return**: when the page becomes visible again, the app asks the browser to check its service worker for a new
  version, at most once a minute. A new worker takes over as today, and the existing notice «فيه نسخة جديدة من
  التطبيق» appears.
- **In Settings**: a line under «المستخدم دلوقتي» shows the running version's code and the date it reached this
  device, and says when a newer version is ready.

The build adds one `<meta>` tag with the version code to the page, and the service worker records when its version
arrived. As in earlier features, the decisions, data model and checks are kept in this file.

## Technical Context

- **Language**: JavaScript in one page (Preact and htm), built by `tools/build.py` from `src/app/*.js`. The service
  worker `sw.js` is generated by the same build.
- **Storage**: no app data. One small entry in the version's own cache (`./version`, decision 3).
- **Tests**:
  - `tools/check-security.js`: the page's Content-Security-Policy;
  - CI's "Generated files match the source" step: the build stays deterministic;
  - `tools/check-code.js`, `tools/check-parity.js`;
  - Playwright E2E in `tests/e2e/version.spec.js` (new).
- **Target**: phone browsers at 375 px, installed to the home screen, offline.
- **Constraints**: no new library, no network beyond the app's own site, no file over 600 lines, no unused code. The
  generated files must stay the same for the same source (CI checks it).

Nothing is left as NEEDS CLARIFICATION.

## Decisions (research)

1. **The check on return asks the browser, it does not fetch on its own.**
   - **Decision**: in `src/app/21-shell.js`, beside the existing `controllerchange` listener, a `visibilitychange`
     listener runs when the page becomes visible. If the last check was a minute or more ago, it calls
     `navigator.serviceWorker.getRegistration()` and then `registration.update()`, inside `catch` so that offline it
     does nothing.
   - **Why**: `update()` makes the browser fetch `sw.js` once, bypassing the HTTP cache (the page registers it with
     `updateViaCache:'none'`). A new file installs as a new worker, which takes over (`skipWaiting`, `clients.claim`),
     and the existing `controllerchange` listener shows the notice (FR-002). No new path is needed for what follows.
   - **Once a minute**: the time of the last check is kept in the effect, not stored. A fresh launch counts as a
     check, because the browser checks on load.
   - **Rejected**: fetching `index.html` and comparing it, which duplicates what the browser already does; a timer,
     which costs battery and does not help a page the phone has suspended.
2. **The page knows its own code from a `<meta>` the build adds after computing it.**
   - **Decision**: `tools/build.py` computes the version from the finished page, as now, and then adds
     `<meta name="mizan-version" content="<code>">` after the charset tag, and writes `index.html` after that. The code
     in the page and in `sw.js` is the same.
   - **Why**: the code is a hash of the page, so the page cannot hold it before it is computed. Adding it afterwards
     keeps the build deterministic: the same source gives the same code and the same files. A `<meta>` is not covered
     by the Content-Security-Policy, so no hash changes.
3. **The date shown is when the version reached this device, not the build date.**
   - **Decision**: the service worker's install step also stores a small response, `./version`, holding
     `{code, at}` (`at`: the install time), in its own cache. Settings reads it with the Cache API.
   - **Why**: a build date written into the files would change on every build of the same source, and CI's
     "Generated files match the source" step would fail. The date the version arrived answers the owner's real
     question («هو الموبايل عنده آخر نسخة؟») just as well: if it arrived today, it is new.
   - **Spec change**: the spec's assumption said "the build date"; it changes to "the date it reached this device"
     (the owner had no preference). Updated in the spec with this plan.
   - **Rejected**: the date of the last git commit, which is not known yet when the files are built before a commit.
4. **What Settings shows.**
   - **Running code**: from the page's `<meta>`.
   - **Installed code**: the one `mizan-<code>` cache the service worker keeps (not `mizan-guides-*`).
   - **The line**:
     - same code: «النسخة: <code> · وصلت <date>»;
     - a different installed code: «النسخة: <code>. فيه نسخة أحدث جاهزة» with «افتحها», which reloads (US2,
       scenario 2);
     - no service worker, or nothing installed yet: «النسخة: <code>» if the `<meta>` is there, else «النسخة: مش
       معروفة», with no error (US2, scenario 3).
   - The date uses the app's own date label. The code is shown in an LTR isolate.

## Data model

- **`<meta name="mizan-version">`** in `index.html`: the 10-character code.
- **`./version`** in the cache `mizan-<code>`: `{"code": "<code>", "at": <milliseconds>}`. It goes with its cache when
  a newer version replaces it.
- **App data**: unchanged.

## Design

### Changes

| File | Change |
|---|---|
| `tools/build.py` | Add the `<meta name="mizan-version">` after computing the version, before writing `index.html` (the version is computed before `index.html` is written, instead of after). In the service worker template, the install step also puts `./version`. |
| `src/app/21-shell.js` | The `visibilitychange` check (decision 1), in the same effect as the `controllerchange` listener. |
| `src/app/15-settings-view.js` | A `VersionLine` in the «المستخدم دلوقتي» panel (decision 4). The file stays under 600 lines (about 385). |
| `README.md` | The «التحديث» part: the app checks when you come back to it, and Settings shows the version. |

### UI copy

- «النسخة: <code> · وصلت <date>»
- «النسخة: <code>. فيه نسخة أحدث جاهزة» and the button «افتحها»
- «النسخة: مش معروفة»

### Tests

- **Build**: two builds of the same source give the same `index.html` and `sw.js` (as CI checks); the code in the
  `<meta>` equals the one in `sw.js`.
- **`tools/check-security.js`**: the policy still covers every inline script and style.
- **`tests/e2e/version.spec.js`** (Chromium and WebKit, generated data):
  - **US1**:
    - with `ServiceWorkerRegistration.prototype.update` counted, the page going hidden and then visible calls it once;
    - a second return within a minute does not; one after a minute does (with Playwright's clock);
    - offline, a return shows no error;
  - **US2**:
    - once the worker is installed, Settings shows the code from the `<meta>` and today's date;
    - with a cache of another code present (put there by the test), the line says a newer version is ready, and
      «افتحها» reloads;
    - in a browser without service workers, the line shows the code or «مش معروفة», with no error.
  - **The notice**: the existing path (a new worker takes over → «فيه نسخة جديدة») is already covered in
    `offline.spec.js` for the worker; this feature only adds the trigger.
- **Parity**: 0 differences.
- **By hand on the owner's phone** (the real test of US1): open the installed app, publish a build, switch away and
  back, and see the notice and the new code in Settings.

## Risks

- **Phones that report no return**: some phones may not fire `visibilitychange` when an installed app comes back
  from the background. Those still update on a full launch, as today (spec, Assumptions). The owner's phone is the
  real test; E2E can only simulate the event.
- **The first update after this ships**: phones on an older version get this feature only after their next full
  launch, since the old version has no check on return. From then on it works.
- **A worker that never installs** (a failed download): the line keeps showing the running code, and the next
  return tries again.
